# コミット・PR運用ガイドライン(Claude Code 向け)

> このドキュメントは Ethotrace 開発における Git 運用の規約である。
> `CLAUDE.md` から必ず参照させること(末尾「CLAUDE.md への組み込み」参照)。

## 0. このルールが存在する理由

このプロジェクトでは、**人間(プロジェクトオーナー)が PR 単位でコードを読み、理解してからマージする**。
コミットログは単なる履歴ではなく、**レビュアーが変更を理解するための物語(narrative)** である。

したがって:

- PR = レビューの単位(機能単位)
- コミット = 理解の単位(意味単位)

「PR にコミットが1つだけ」はこのプロジェクトでは**規約違反**である。作業の最後にまとめて1コミットするのではなく、**意味単位が完成するたびにコミットする**こと。

## 1. ワークフロー全体

1. マイルストーン内のタスクを**機能単位**に分割する(分割案はオーナーと合意済みか、PR説明で提示する)。
2. 機能単位ごとにブランチを切る: `m1/reentrancy-guard` のように `m<番号>/<機能名>` 形式。
3. **作業を始める前に、その PR で積む予定のコミット計画を立てる**(§3)。
4. 意味単位ごとに実装 → テスト → **コミット**を繰り返す。
5. PR を作成。説明文にコミット計画(実績)と読み順を記載する(§5)。
6. オーナーのレビュー・マージを待つ。**マージ前の squash は行わない**(コミットの物語を保存するため)。

### マージ方式(確定事項)

コミットログはこのプロジェクトの**資産**であり、squash せず意味のあるコミットを積み上げて残す。

- マージは **merge commit 方式(`--no-ff` 相当)** のみ。squash merge / rebase merge は使わない。
- リポジトリ初期設定(M0)で、GitHub の Settings → Pull Requests から **"Allow squash merging" と "Allow rebase merging" を無効化**し、"Allow merge commits" のみ有効にする。規約を設定レベルで強制する。
- この方式により履歴は2階層の物語になる:
  - `git log --first-parent main` — PR(機能単位)レベルの粗い物語
  - `git log` — コミット(意味単位)レベルの詳細な物語
- マージコミットの件名は GitHub 既定(`Merge pull request #N ...`)のままでよいが、PR タイトルが機能単位を表す名前になっていることを確認する。

## 2. コミットの意味単位とは

### 1コミット = 1つの論理的変更

「この変更は何のためか」を一文で言えて、その一文に「と」「また」が入らない大きさ。

### 必ず分離するもの

| 分離対象 | 理由 |
|---|---|
| 振る舞いの変更 と リファクタリング | リファクタは「テストが変わらない」ことが正しさの根拠であり、混ぜると検証不能になる |
| 機械的変更(rename、rubocop自動修正、ファイル移動)と 手書きの変更 | 機械的変更は diff が大きくてもレビュー10秒、混ぜると手書き部分が埋もれる |
| 依存追加(Gemfile/gemspec 変更)と それを使う実装 | 依存の妥当性は独立に判断したい |
| 設計ドキュメント・スキーマの更新 と 実装 | ただし小さな同時更新(コメント修正等)は実装に含めてよい |

### テストとの関係

- **テストは対応する実装と同じコミットに含める**のを基本とする(コミット単体で「何を保証するか」が閉じる)。
- TDD の red → green を分けたい場合は、red コミットを作ってよいが、件名に `test(red):` を付け、**push 前にそのコミット時点でも CI が落ちない構成**(pending 指定等)にすること。
- 全コミットで **テストグリーン + ビルド可能** を保つ(`git bisect` 可能性の維持)。コミット前に必ずテストを実行する。

### 粒度の目安

- 1コミットの diff はおおむね **±150行以内**(機械的変更を除く)。超えそうなら分割を検討。
- 逆に「typo修正だけ」「1行だけ」の極小コミットを乱発しない。直前コミットの修正は、**push 前に限り** `git commit --amend` または `git rebase -i` での統合を許可する。**push 済みコミットの書き換えは禁止**。

## 3. コミット計画(作業前に立てる)

実装に着手する前に、積む予定のコミット列を箇条書きで作る。例(M1「再入ガード」機能の場合):

```
計画:
1. test: 再入ガードの仕様をテストとして記述(pending)
2. feat(core): Thread-local 再入フラグと guard API を実装、テストを有効化
3. feat(core): Tracker の記録パスすべてに guard を適用
4. test: 自己再帰シナリオ(wrap されたメソッドが Tracker を呼ぶ)の回帰テスト
5. docs: §4.5 の実装注記を実態に合わせて更新
```

計画は作業中に変わってよい。変わった場合は PR 説明に実績を書けばよく、計画への完全一致は求めない。**重要なのは「最後にまとめて1コミット」を構造的に不可能にすること**である。

## 4. コミットメッセージ規約

Conventional Commits をベースにする:

```
<type>(<scope>): <件名(日本語可、50字目安、何をしたか)>

<本文(日本語)>
- なぜこの変更が必要か(What ではなく Why)
- 設計上の判断があれば、その選択肢と採用理由
- 設計資料の関連節があれば参照(例: 設計資料 §4.5)

Refs: #<issue番号>(あれば)
```

- **type**: `feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `perf` / `ci`
- **scope**: gem 名の短縮形 — `core`, `rspec`, `minitest`, `rails`, `mcp`, `rbs`。リポジトリ全体に関わる場合は省略可。
- 件名は「何をしたか」、本文は「なぜか」。**本文のないコミットは `chore` と機械的変更のみ許可**。

例:

```
feat(core): CallContext スタックを Thread-local 化

Fiber/Thread をまたぐとコンテキストが混線するため、
スタックを Thread.current キーで分離した(設計資料 §4.3)。
Fiber スケジューラ下の挙動は v1 ではベストエフォートとし、
既知の制約として §8-10 に記載済み。
```

## 5. PR の規約

- **1 PR = 1 機能単位**。目安として diff 合計 ±400 行以内(lock ファイル・機械的変更を除く)。超える場合は PR 自体を分割する。
- PR 説明テンプレート:

```markdown
## 目的
(この機能単位が何を達成するか、1〜3行)

## コミットの読み順
1. <sha> test: ... — ここで仕様が読める
2. <sha> feat(core): ... — 本体。設計判断は本文参照
3. ...

## 設計資料との対応
(該当する § を列挙。資料からの逸脱があれば明記して理由を書く)

## レビューしてほしい点
(自信のない判断、代替案があった箇所)
```

- 「コミットの読み順」は通常コミット順だが、**先に読むべきコミットが後ろにある場合は明示する**。

## 6. アンチパターン(禁止事項)

1. **作業完了後の一括コミット**。`git add -A && git commit` で全部入り1コミットを作らない。万一作業が混ざってしまったら `git add -p` で意味単位に分割してからコミットする。
2. **push 済み履歴の rebase / force-push**(オーナーの明示指示がある場合を除く)。
3. **マージ前 squash**。コミットの物語がレビューの成果物なので潰さない。
4. 「fix」「update」「wip」だけの件名。
5. 振る舞い変更とリファクタの混在(§2)。
6. テストが落ちる状態でのコミット(`test(red):` の例外を除く)。
7. 無関係ファイルの巻き込み(エディタ設定、tmp、観測データ `tmp/ethotrace/` 等)。コミット前に `git status` と `git diff --staged` を確認する。

## 7. セルフチェック(コミット直前に毎回)

- [ ] このコミットの目的を一文で言えるか(「と」が入らないか)
- [ ] テストは通っているか
- [ ] 振る舞い変更とリファクタが混ざっていないか
- [ ] `git diff --staged` に無関係ファイルがないか
- [ ] 本文に Why を書いたか

## CLAUDE.md への組み込み

`CLAUDE.md` に以下を追記すること:

```markdown
## Git 運用
- コミットと PR の運用は docs/commit-guidelines.md に**必ず**従う。
- 要点: 1 PR = 1 機能単位、1 コミット = 1 意味単位。作業前にコミット計画を立て、
  意味単位が完成するたびにコミットする。最後の一括コミットは禁止。
- 全コミットでテストグリーンを維持する(コミット前にテスト実行)。
```
